# 架构与设计取舍

## 内容处理

采集端通过 `ContentCollector` 适配 GitHub、RSS 和 `DEMO` 数据源。内容先标准化，再用 `(source_name, external_id)` 与 `content_hash` 双重约束去重。文章提交成功后才创建分析任务，避免分析尚未持久化的内容。

任务记录保存在 `pipeline_tasks`：任务有稳定幂等键、状态、执行次数、下次重试时间与错误信息。调度器负责领取任务，失败后按重试策略重新入队；因此服务重启不会丢失待处理工作。

## AI 分析与缓存

分析结果通过 `(article_id, content_hash, model_used, prompt_version)` 唯一约束保存，避免同一版本重复调用模型。热点、兴趣画像与推荐结果使用 Redis 缓存；Redis 不可用时查询退回 MySQL，核心浏览链路仍可工作。

## 研究助手

研究助手不是任意网络浏览器。它只能从下列白名单工具中选择，且单次请求最多使用三个工具：

- 站内情报检索
- GitHub 趋势查询
- 用户兴趣匹配

每次调用都会保存输入、输出、状态、耗时和 Trace。模型获得的事实材料来自 `Evidence`，最终回答通过编号引用关联来源；工具失败不会被伪造成成功结果。

## 可观测性

请求入口生成或复用 `X-Trace-Id`，并通过异步任务装饰器传播 MDC。管理端可按 Trace 查询流水线记录；Actuator 提供 MySQL、Redis、GitHub 与模型配置的健康信息。

## 边界

- 当前任务调度依赖单应用实例的数据库领取机制；多实例部署前应验证并强化任务抢占与幂等策略。
- AI 输出可能不准确，引用表示证据来源而非对生成内容的担保。
- 公开部署时应配置受限 CORS 来源、强随机 JWT 密钥、密钥管理和访问限流。
